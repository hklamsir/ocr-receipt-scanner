## ADR-001「裁切圖片超額靜默丟圖 — 改採雙層防護」

- **狀態**：Accepted
- **日期**：2026-08-24
- **決策者**：Lamsir（用戶）、WorkBuddy

### 背景（Context）
用戶回報：用手機相機拍攝單據並經 Gemini Vision OCR 時，
- **不裁切**：圖片可成功儲存；
- **先裁切才 OCR**：單據資料能存，但圖片未能入庫（兩者單據資料都存到）。

詳細調查見 `docs/investigation_crop_unsaved.md`，根因為「圖片 dataURL 體積超過後端上限，後端靜默放棄圖片」：

1. **不裁切路徑（成功）**：拍照經 `js/modules/utils.js` 的 `compressImage()` 縮至 1200px 寬並逐步降質，使 base64 `< appConfig.maxImageSizeKb`（預設 200KB，二進位 ≤153KB）→ 後端大小檢查通過 → 存圖 ✅
2. **裁切路徑（失敗）**：`js/app.js` 的 `applyCrop()` 以 `cropQuality = min((imageQuality/100)+0.2, 0.95) = 0.8` 固定較高品質重新編碼（`canvas.toDataURL('image/jpeg', 0.8)`），**完全沒有再壓到大小上限**。裁切圖二進位通常 225–500KB+，超過後端 `MAX_IMAGE_SIZE_KB*1024+500 ≈ 205KB`。
3. **後端靜默放棄**：原 `api/save_receipts.php`（第 150–159 行）當 `$imageSize > $maxImageBytes` 時，僅 `logError("Image too large ...")` 並**繼續寫單據列、`image_filename = null`**，回傳仍是 `success` → 前端只見「儲存成功」。
4. **Vision 模式綁定時機**：`item._imageDataUrl` 於 OCR 當下綁定（`app.js:319` 取 `r.value.image = img.dataUrl`，`js/modules/ocr.js:149`）：
   - 裁切→才 OCR：OCR 時 `img.dataUrl` 已是裁切後大圖 → 後端丟圖 ✗
   - OCR→才裁切：OCR 時仍是原始小圖 → 後端存圖 ✓

MIME 並非差異點（兩者皆 `image/jpeg`，皆過 magic bytes 檢查）。

### 決策（Decision）
採**雙層防護**：前端治本 + 後端自救並明確告知。

1. **前端（治本）**：`applyCrop()` 裁切輸出後套用與 `compressImage` 相同的大小預算邏輯。
   - 新增 `recompressCroppedCanvas()`：以 `dataURL.length > maxImageSizeKb * 1024` 為閾值，先在原尺寸逐步降質（0.8→0.3），仍超標則縮至 1200px 再降質，結果寫回 `images[idx].dataUrl`。
   - 確保 OCR 送出的 `_imageDataUrl` 已符合後端上限。
2. **後端（防禦 + 明確告知）**：新增 `recompressImageToLimit()`（依賴 GD 擴充）。
   - 超過 `MAX_IMAGE_SIZE_KB` 時伺服器端重新壓縮：原尺寸降質失敗則縮至 1200px 再降質；成功則存圖。
   - 若 GD 不可用或仍壓不下：單據照存、`image_filename = null`，並在成功回應帶 `warning` 欄位。
   - 前端成功分支以 `Toast.warning` 顯示 `result.warning`，使用者能明確得知圖片被略過。

### 影響（Consequences）
- **正面**：絕大多數裁切場景前端已壓好，後端作為極端自救 + 明確提示，不再出現「靜默丟圖」。
- **前提**：後端重新壓縮依賴 PHP **GD 擴充**（InfinityFree 一般已啟用）。若 GD 不可用，後端走「略過圖片 + warning」分支；而前端已保證圖片不超額，故不會回到舊問題。
- **驗證**：`js/app.js` 已通 Node ES module 語法檢查；後端 `api/save_receipts.php` 經人工逐行審查（本機當時無 PHP 未能 `php -l`，待部署實測）。本機現已安裝 PHP 8.5.9，後續可直接 `php -l` 校驗。
